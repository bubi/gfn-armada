## The open blocker, precisely

In a real stream Chromium falls back to
`FFmpeg (fallback from: ExternalDecoder (VaapiVideoDecoder))`. The instrumented
driver exposes the full decode phase:

```text
va init
va create_config id=1 profile=13      # HEVC Main
va create_config id=2 profile=7       # H.264 High
session open node=/dev/video0 mode=display-order codec=H264 1920x1088
va create_context id=3 profile=7 1920x1088 targets=0
va destroy_context id=3 pending=0     # 13 ms later
```

During GPU initialization Chromium queries every profile (6, 7, 13, 17, 18, 19)
and receives answers. During decoding it calls **neither `querySurfaceAttributes`
nor `createSurfaces`**. Failure occurs in Chromium's own frame-pool setup without
reaching the driver. Chromium reports no error line.

## Investigated and ruled out — do not retry blindly

* **GPU sandbox.** `--disable-gpu-sandbox` changed nothing; the trace shows
  `session open node=/dev/video0` in the GPU process with the sandbox enabled.
* **Missing DRM_PRIME_2 import.** Patch written, builds with `-Wall -Wextra`,
  upstream suite passes; no effect because Chromium never requests surfaces.
* **The two kernel patches.** `supports_import()` is read only in
  `publish_policy()`, called only from `submit()` (`picture.cc:55`). There is
  no `submit` in the trace, so these patches cannot affect the blocker. They
  would address B-frame deadlock and zero-copy; neither causes this failure.
* **UA spoofing.** `compatibility_user_agent` defaults to `true`; the measurement
  used it. Codec selection uses SDP, not headers.
* **AV1.** At this stage GFN disables it server-side for Linux:
  `"disableConfigList":[…,"PLT=LINUX;COD=AV1",…]`.
* **Mesa as a V4L2-to-VA-API bridge.** No such bridge exists here; Freedreno has
  no video decode. Installed VA drivers are Mesa Gallium only.

## Known pitfalls for the next round

* **Chromium logs.** Logging initializes before the JS entry point, so
  `app.commandLine.appendSwitch('vmodule',…)` has no effect — INFO appears,
  VERBOSE never does. Switches must be on argv. The launcher **deliberately**
  rejects arbitrary runtime flags (`tests/launcher.test.cjs:82`) to prevent
  `--no-sandbox` entering through Steam launch options. Preserve this guarantee;
  use a diagnostic entry point through `package.json` `main`, as the project does.
* **GFN starts no session in the diagnostic entry point** (0 samples in 110 s),
  but starts reliably in the production client. The decisive log is missing there.
* **Single-instance lock.** An existing client makes a new launch silently exit
  with code 0 and no output. Stop and verify all main processes before launching.
* **`XAUTHORITY`** changes each session (`/run/user/1000/xauth_*`). Hardcoding it
  produces “Missing X server” and an empty log. Resolve it dynamically.
* **macOS `tar`** includes AppleDouble files that the ARM64 test glob picks up
  as tests. Use `COPYFILE_DISABLE=1 tar --no-xattrs`.
* **Environment allowlist.** The supervisor passes only fixed variables to the
  helper; test fixtures must not depend on environment configuration.
